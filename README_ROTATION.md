# Планирование ротации операторов

## Назначение

Планинг ротации ILU-Project формирует **рекомендательный календарь временных перемещений операторов** между производственными постами. Его задача — поддерживать освоенные компетенции и не допускать длительных перерывов в работе на постах, где оператор уже имеет уровень **L** или **U**.

Генератор не распределяет людей случайным образом: он использует историю фактической расстановки, определяет очередность ротаций и проверяет, можно ли выполнить перемещения без потери необходимого покрытия постов.

## Какие данные учитываются

- **Матрица ILU:** список операторов, постов и уровни компетенций.
- **Явка:** участвуют только операторы со статусом `Я` или `Явка`.
- **Роли:** `НУ`, `СО` и `ДС` исключены из кандидатов на ротацию.
- **Фактическая расстановка:** текущие отметки `○` задают исходную занятость постов. Отметка `△` не используется как исходная занятость.
- **Журнал расстановки:** дата последней работы конкретного оператора на конкретном посту.
- **Настройки генератора:** продолжительность одного блока ротации в рабочих днях и максимальное количество одновременно выполняемых цепочек.
- **Месяц планирования:** текущий или выбранный для просмотра месяц.

**Важно:** оператор может быть направлен на пост только при уровне **L** или **U**. Уровни `I`, `Iкр`, `Lкр` и отсутствие компетенции не подходят для автоматической ротации.

## 1. Определение потребности в ротации

Генератор рассматривает каждую допустимую пару **«оператор — пост»** и находит последнюю дату работы по журналу расстановки.

Если запись есть, контрольный срок рассчитывается как **последняя работа + 3 календарных месяца**. Это именно календарные месяцы, а не фиксированные 90 дней. Если соответствующего числа в целевом месяце нет, используется последний день этого месяца.

Потребности распределяются по трём категориям:

| Очерёдность | Категория в коде | Условие |
|---|---|---|
| **1** | `overdue` — просрочено | Трёхмесячный срок истёк **до начала планируемого месяца** |
| **2** | `unknown` — нет истории | В журнале нет корректной даты работы оператора на данном посту |
| **3** | `upcoming` — предстоящая | История есть, но срок не истёк до начала месяца |

### Что происходит, если оператор никогда не стоял на посту

Если у оператора есть **L/U**, но в журнале нет записи по этому посту, генератор присваивает паре категорию **«Нет истории»**. Такая потребность имеет **второй приоритет: после просроченных и перед предстоящими**.

Отсутствие записи не доказывает, что оператор действительно никогда не работал на посту: возможно, журнал начали вести позже. Генератор воспринимает оба случая одинаково.

### Порядок внутри категорий

- Среди **просроченных** первыми рассматриваются случаи с наибольшей просрочкой.
- Среди **предстоящих** — случаи с ближайшим контрольным сроком.
- Для категории **«Нет истории»** генератор старается выравнивать количество уже назначенных основных блоков между операторами.
- Если показатели равны, используется стабильный порядок операторов и постов в матрице.

Оператор, который **уже стоит на том же посту с отметкой `○`**, не включается в список потребностей для ротации на этот пост.

## 2. Исходная расстановка

Перед расчётом система создаёт **виртуальную копию** текущей расстановки по отметкам `○`.

Пост считается исходно покрытым, если на нём стоит оператор с уровнем **L/U**. Генератор старается сохранить такое покрытие в течение всех запланированных перемещений.

При этом реальная матрица и фактические отметки расстановки **не меняются**: алгоритм моделирует возможные перемещения только внутри планирования.

## 3. Построение цепочек перестановок

Главная особенность генератора — он планирует не только одного оператора на целевой пост, но при необходимости **всю цепочку замещений**.

Например, требуется направить Иванова на пост № 2, но Иванов уже работает на посту № 1, а пост № 2 занят Петровым. Генератор ищет допустимый вариант, при котором Петров и, если необходимо, другие операторы перемещаются на доступные посты. Если нужно, цепочка замыкается возвратом одного из участников на исходный пост Иванова либо завершается подключением свободного подходящего оператора.

Для каждого участника проверяется компетенция **L/U** на целевом посту. Если после перемещения какой-либо исходно покрытый пост останется без подходящего оператора, цепочка отклоняется.

В некоторых случаях допустима **открытая цепочка**: свободный основной оператор занимает нужный пост, а вытесненный оператор временно освобождается в рамках планового блока. Такая запись — элемент виртуального расчёта, а не фактическое снятие человека с поста.

**Результат:** генератор не должен назначать ротацию ценой потери исходно обеспеченного производственного покрытия.

## 4. Выбор подходящей цепочки

Для каждой потребности могут существовать разные допустимые варианты. Генератор сравнивает их последовательно:

1. **Меньше участников в цепочке** — предпочтительнее простая перестановка.
2. **Больше закрытых потребностей** — одна цепочка может одновременно решить задачи ротации нескольких операторов.
3. **Выше суммарная срочность** — просроченные потребности ценятся выше отсутствующей истории, а те — выше предстоящих.
4. Для потребностей **без истории** учитывается распределение назначений по месяцу, чтобы по возможности не концентрировать их в одном периоде.
5. При прочих равных используется стабильный порядок участников, постов и дат.

Это означает, что самый срочный кандидат не всегда получит первый календарный блок: вариант должен быть **выполнимым** с учётом занятости и замещений.

## 5. Размещение в календаре

Каждая выбранная цепочка назначается на **последовательность рабочих дней** заданной продолжительности.

По умолчанию, если настройки не заданы:

- **5 рабочих дней** — продолжительность блока;
- **2 цепочки одновременно** — максимальная параллельность.

Субботы и воскресенья пропускаются. Отдельный производственный календарь праздников в рассматриваемом алгоритме не применяется.

Для каждого дня блока проверяется:

- не превышен ли лимит одновременно активных цепочек;
- не участвует ли оператор уже в другой цепочке в этот день;
- не задействован ли тот же целевой пост другой цепочкой;
- остаётся ли виртуальная расстановка допустимой после перестановок.

Если подходящего блока или безопасной цепочки нет, потребность **не включается в план**. Генератор продолжает искать варианты для других потребностей; неудача одного кандидата не останавливает весь месяц. После размещения доступных цепочек выполняется дополнительный проход по оставшимся потребностям.

## 6. Пример приоритетов

План строится на октябрь:

| Оператор | Пост | Последняя работа | Категория |
|---|---|---|---|
| Иванов | № 10 | 12 июня | Просрочено: срок 12 сентября |
| Петров | № 20 | Записи нет | Нет истории |
| Сидоров | № 30 | 20 августа | Предстоящая: срок 20 ноября |

При прочих равных генератор сначала попробует обеспечить ротацию Иванова, затем Петрова, затем Сидорова. **Но только при наличии допустимых цепочек и свободных календарных блоков.**

## 7. Результат генерации

План отображается в календарной таблице:

- **строки** — производственные посты;
- **столбцы** — дни выбранного месяца;
- **ячейки** — назначенные операторы;
- **выходные** — выделены отдельно.

Ячейки автоматических назначений связаны с идентификатором цепочки. Генератор также формирует служебные сведения о цепочках, их участниках, основных потребностях и том, какие потребности удалось запланировать.

Пустая ячейка означает, что автоматического назначения на данный пост в этот день нет. Она **не означает**, что пост фактически будет пустовать: календарь показывает именно ротационные перемещения, а не полную ежедневную расстановку.

## 8. Ручная корректировка

В календаре предусмотрено ручное редактирование:

- нажатие на пустую ячейку `+` — выбор оператора для указанного поста и дня;
- нажатие на заполненную ячейку — удаление непрерывного фрагмента назначения этого оператора на данном посту.

Для ручного добавления доступны только операторы **с явкой и уровнем L/U** на выбранном посту. Дополнительно проверяется, не назначен ли тот же оператор на другой пост в этот день.

**Ограничение:** ручное добавление работает с ячейками календаря и не повторяет весь механизм автоматического построения безопасных цепочек. После ручных изменений план необходимо проверить на производственную реализуемость.

## 9. Что генератор не делает

- Не изменяет уровни ILU и не повышает квалификацию.
- Не меняет фактические отметки `○`/`△` в матрице.
- Не создаёт автоматически записи о фактической работе в журнале расстановки.
- Не гарантирует выполнение всех потребностей в пределах одного месяца.
- Не учитывает праздничные дни отдельно от обычных будней.
- Не заменяет решение начальника участка о реальной расстановке персонала.

## Кратко об алгоритме

**Компетенции L/U → явка и текущая расстановка → история по журналу → приоритеты (просрочено → нет истории → предстоящая) → безопасные цепочки перестановок → календарные блоки → план ротации.**
