# ILU SE-4 90 — README для разработчиков и сопровождения

Этот документ предназначен для разработчиков, ответственных за поддержку и развитие приложения. Пользовательская инструкция находится отдельно в `README_ILU_Project.md`.

## 1. Назначение приложения

Приложение работает в браузере и предназначено для ведения матрицы квалификации ILU:

- матрица постов и операторов;
- уровни владения постом (`Iкр`, `I`, `Lкр`, `L`, `U`);
- явка, роли и эргономика;
- обучение операторов;
- журнал расстановки;
- планы развития и ротации;
- статистика участка;
- экспорт текущей таблицы в Excel-совместимый файл.

Сейчас это клиентское приложение без сервера. Данные хранятся в `localStorage` конкретного браузера и профиля пользователя.


Не смешивайте пользовательскую документацию с технической: изменения в интерфейсе описываются в пользовательском README, изменения архитектуры и хранения — здесь.

## 3. Порядок загрузки скриптов

Порядок в `matrix.html` является частью архитектуры и менять его без проверки зависимостей нельзя:

```html
<script src="storage.js"></script>
<script src="app-state.js"></script>
<script src="placement-module.js"></script>
<script src="training-module.js"></script>
<script src="plans-module.js"></script>
<script src="matrix-rules.js"></script>
<script src="ui-module.js"></script>
<script src="matrix-render.js"></script>
<script src="matrix-actions.js"></script>
<script src="app.js"></script>
<script src="plans-storage.js"></script>
<script src="excel-export.js"></script>
```

Причины:

1. `storage.js` предоставляет `loadState()` и `saveState()`.
2. `app-state.js` создаёт глобальные массивы и вызывает восстановление состояния.
3. Остальные модули используют это состояние и функции соседних модулей.
4. `plans-storage.js` оборачивает функции планов, уже объявленные в `plans-module.js` и запущенные через `app.js`, поэтому он подключается поздно.
5. `excel-export.js` подключается последним и использует готовую DOM-матрицу и функции интерфейса.

Проект использует обычные классические `<script>`, а не ES-модули. Общие переменные доступны через глобальную область видимости, поэтому при переименовании нужно искать все обращения по проекту.

## 4. Ответственность модулей

### `app-state.js`

Хранит данные предметной области и UI-состояние:

- `posts`, `operators` — списки постов и операторов;
- `data` — матрица уровней размером `posts.length × operators.length`;
- `attendanceData` — текущая расстановка (`''`, `○`, `△`);
- `difficulty`, `ergonomics`, `trainingDays` — свойства постов;
- `operatorAttendance`, `operatorRoles` — явка и роли операторов;
- `trainingRecords`, `placementLog` — журналы;
- `placementFilters`, `placementSort` — фильтры и сортировка журнала;
- `filterState`, `workshopChief`, `sectionChief` — выбранная структура и руководители.

Матрицы используют параллельные индексы: строка `r` относится к `posts[r]`, столбец `c` — к `operators[c]`. Добавление или удаление оператора должно синхронно менять все массивы, содержащие данные по операторам.

### `storage.js`

Сохраняет основное состояние в `localStorage` под ключом:

```text
ilu-se4-state-v1
```

При загрузке выполняется проверка массивов и размеров матриц. Сохранение вызывается из действий и рендера, поэтому после изменения данных нужно убедиться, что вызывается `saveState()` либо функция, которая его вызывает.

### `plans-storage.js`

Хранит планы отдельно под ключом:

```text
ilu-se4-plans-v1
```

Планы не следует добавлять в объект основного состояния без отдельной миграции: это нарушит разделение данных и усложнит резервное копирование.

### `matrix-rules.js`

Содержит производственные правила, а не отрисовку. Основные правила:

- активными считаются статусы `○` и `△`;
- перевод обученного оператора из `I` отображается как `Lкр` при постановке на пост;
- квалифицированные уровни: `L`, `Lкр`, `U`;
- допустимые сочетания квалифицированных операторов: `Iкр + U`, `Iкр + L`, `Iкр + Lкр`;
- сочетания `U + U`, `L + L`, `U + L` запрещены;
- при добавлении квалифицированной расстановки несовместимая старая квалифицированная расстановка снимается согласно производственному правилу.

Изменяя правила, обновляйте одновременно проверку действия, визуальную подсказку и тестовый чек-лист.

### `matrix-render.js`

Отвечает за построение таблицы, классы цветов, отображение уровней и статистику (заполненность, обучение, поливалентность). Рендер не должен самостоятельно менять бизнес-данные, кроме предусмотренного сохранения состояния после изменения.

### `matrix-actions.js`

Обрабатывает действия пользователя:

- цикл статуса поста и уровня квалификации;
- добавление, редактирование и удаление постов/операторов;
- изменение явки, роли, сложности, эргономики и срока обучения;
- редактирование руководителей.

При удалении оператора он исчезает из текущей матрицы, но записи в журналах должны сохраняться. Это намеренное производственное поведение: история уволившихся операторов не удаляется.

### `training-module.js`

Создаёт и изменяет записи обучения, вычисляет окончание обучения и отображает журнал. Статус `△` в матрице связан с обучением, поэтому при изменении этого поведения нужно проверить и матрицу, и журнал обучения.

### `placement-module.js`

Добавляет записи фактической расстановки, строит журнал, применяет фильтры по датам/операторам/постам и сортировку. Журнал является историей и не должен очищаться при удалении оператора.

### `plans-module.js`

Отвечает за календарь развития и ротации: создание, редактирование, размещение и удаление пунктов планов. Сохранение выполняется слоем `plans-storage.js`.

### `ui-module.js`

Содержит операции интерфейса, не относящиеся к правилам матрицы: вкладки, выпадающие меню, фильтры, дата, информационная карточка и обработчики общего UI.

### `excel-export.js`

Экспортирует текущую таблицу в Excel-совместимый HTML-файл с расширением `.xls`. Это не настоящий бинарный `.xlsx`; при изменении разметки матрицы нужно проверить экспорт отдельно.

## 5. Жизненный цикл запуска

1. Браузер загружает `matrix.html` и скрипты в указанном порядке.
2. `app-state.js` создаёт начальные данные и вызывает `loadState()`.
3. Сохраняются выбранные фильтры участка, если они были в состоянии.
4. `app.js` обновляет дату, информационные карточки и запускает первичный рендер:
   `renderMatrix()`, `renderTrainingTable()`, `renderPlacementLog()`.
5. Действия пользователя меняют глобальное состояние, перерисовывают нужный блок и сохраняют данные.

Если интерфейс загружается, но таблица пустая, сначала проверяйте консоль и порядок `<script>`, затем размеры `posts`, `operators`, `data` и `attendanceData`.

## 6. Хранение и резервное копирование

Данные привязаны к origin браузера. Поэтому `file://` и `http://localhost` могут иметь разные хранилища. Очистка данных сайта, другой браузер или другой профиль не переносят матрицу автоматически.

Для ручной резервной копии в DevTools выполните:

```js
copy(localStorage.getItem('ilu-se4-state-v1'))
copy(localStorage.getItem('ilu-se4-plans-v1'))
```

Перед импортом/восстановлением сохраняйте текущие значения. Не редактируйте JSON вручную без копии: ошибка формата может привести к откату к начальному состоянию.

В будущем для многопользовательской версии потребуются серверное хранилище, авторизация, разделение участков и миграции схемы. Текущая версия этого не обеспечивает.

## 7. Запуск для разработки

Для пилотной проверки приложение можно открыть через `matrix.html`. Для регулярной разработки предпочтителен локальный HTTP-сервер — так устраняются особенности `file://`, в том числе предупреждения DevTools о разных security origins:

```bash
python -m http.server 8000
```

Затем откройте `http://localhost:8000/matrix.html`.

При переносе файлов в подпапки обновляйте пути в `matrix.html` и проверяйте Network в DevTools. `net::ERR_FILE_NOT_FOUND` обычно означает неправильный путь к скрипту, картинке или стилю, а не ошибку JavaScript.

## 8. Проверка перед передачей версии

Минимальный чек-лист:

- открыть приложение без ошибок `SyntaxError`, `ReferenceError` и `TypeError`;
- проверить загрузку всех ресурсов во вкладке Network;
- добавить, изменить и удалить оператора;
- убедиться, что удалённый оператор исчез из матрицы, но его история осталась;
- изменить уровень на посту и проверить ограничения совместимости;
- проверить переход `○`/`△`, запись обучения и дату окончания;
- добавить запись в журнал расстановки, проверить фильтры и сортировку;
- создать и изменить пункты планов развития/ротации;
- перезагрузить страницу и убедиться, что данные восстановились;
- проверить экспорт Excel и печать/PDF;
- проверить пустые списки и ситуацию с новым оператором без истории;
- проверить резервную копию `localStorage` до публикации.

Для синтаксической проверки JavaScript:

```bash
for f in *.js; do node --check "$f" || exit 1; done
```

## 9. Правила безопасных изменений

1. Сначала определить, к какому модулю относится изменение. Не добавлять новую бизнес-логику в `app.js`.
2. Не переименовывать глобальные переменные без поиска по всем `.js` и `matrix.html`.
3. При изменении массива операторов проверять все параллельные массивы и обе матрицы.
4. При изменении формата состояния обновлять ключ версии или писать миграцию в `storage.js`.
5. При изменении функций планов не переносить `plans-storage.js` выше `app.js`.
6. После каждого изменения проверять холодный старт, восстановление из `localStorage` и чистый браузерный профиль.
7. Не удалять журналы вместе с оператором без отдельного согласования: история — часть производственного учёта.

## 10. Известные ограничения и технический долг

- нет серверной синхронизации и разграничения прав;
- `localStorage` ограничен одним браузером/профилем и объёмом хранилища;
- отсутствует полноценная система миграций состояния;
- запуск через `file://` может давать предупреждения безопасности и разные хранилища;
- классические скрипты используют глобальную область видимости;
- экспорт Excel — HTML-совместимый `.xls`, а не `.xlsx`;
- переменная `restoredState` используется как признак восстановления, но сама по себе не является отдельным слоем состояния.

## 11. Работа с Git

Перед тестированием новой версии:

```bash
git status
git add .
git commit -m "chore: checkpoint before pilot testing"
```

В коммит должны попасть исходные файлы и документация, но не временные выгрузки, резервные JSON и пользовательские данные. Для каждой заметной функции лучше создавать отдельный коммит — так проще откатить проблемное изменение после тестирования руководителями.

Перед публикацией зафиксируйте в сообщении коммита, что проверено: матрица, обучение, расстановка, планы, восстановление состояния и экспорт.
