# Планирование развития компетенций операторов

Планинг развития формирует месячный календарь обучения. Генератор оценивает, сколько операторов имеют L/U на каждом посту и сколько постов каждый оператор освоил на L/U. Плановые назначения увеличивают эти показатели в модели расчёта. Фактические уровни и расстановка в матрице сохраняются до действий в журнале обучения или матрице.

## Исходные данные и ограничения

- Основные кандидаты исключают роли `НУ`, `СО` и `ДС`. Генератор развития учитывает `○` как занятость. Основной отбор не проверяет явку и не использует `△` как занятость.
- На целевом посту подходят `Lкр`, `I`, `Iкр` и отсутствие уровня, включая пустую строку, `null` и `0`. Для оператора без единого L/U первый виртуальный шаг допускается на постах C с зелёной или жёлтой эргономикой либо B с зелёной.
- По умолчанию в расчёте действует лимит **2 обучения на оператора**. Генератор читает `maxOperatorTrainings` и поддерживает значение `unlimited`. Штатный диалог настроек сохраняет другой параметр, `maxConcurrentTrainings`, который ограничивает одновременные обучения в календаре.
- По паре оператор–пост создаётся максимум одно назначение в рамках генерации. Для каждого поста с `Lкр + ○` генератор сначала пытается добавить продолжение обучения первого подходящего оператора и блокирует пост для новых кандидатов. Продолжение также проходит проверку лимита и возможности освобождения.
- Модель оценивает освобождение с текущих постов по виртуальному покрытию. Если снять занятого оператора без замещения нельзя, генератор ищет цепочку. Приоритет уровней замещения — `Lкр → I → L → U`, далее свобода, меньшая исходная поливалентность и порядок в матрице. Для резерва `ДС` дополнительно проверяются свобода и статус `С`. Такая модель допускает замещение уровнями `I` и `Lкр` и опирается на виртуальное покрытие, поэтому итоговую расстановку проверяют перед применением.

## Порядок генерации

После продолжений обучения алгоритм проходит ступени «посты 2L → операторы 2L → посты 3L → операторы 3L» и далее в пределах условий остановки. Число в названии ступени означает целевое количество L/U, а L/U — фактические значения уровней, учитываемые в расчёте.

| Этап | Порядок отбора |
| --- | --- |
| Посты до N | Посты с покрытием ниже N идут по возрастанию покрытия, затем по порядку в матрице. Среди допустимых кандидатов порядок такой: `Lкр → I → Iкр → пусто`, свободный оператор, меньшая виртуальная поливалентность, индекс оператора. |
| Операторы до N | Допустимые операторы с виртуальной поливалентностью ниже N группируются по наименьшему **числу уже запланированных обучений**. В группе сначала рассматривается оператор с меньшим числом выполнимых вариантов, затем по индексу. |
| Выбор поста для оператора | `qualification → free → coverage → rarity → index`. После приоритета уровня и свободы сравнивается меньшее виртуальное покрытие L/U. При равенстве предпочтителен пост, подходящий меньшему числу участников текущей группы по уровню и допуску к первому L. Последний критерий — индекс поста. |

После каждого принятого назначения виртуальное покрытие и поливалентность увеличиваются на единицу. `rarity` описывает спрос внутри текущей группы. Полное освобождение отдельно проверяется для вариантов конкретного оператора.

## Длительность и календарь

| Уровень на целевом посту | Автоматическая длительность |
| --- | --- |
| `Lкр` или `I` | 10 рабочих дней |
| `Iкр` или отсутствие уровня | Норматив поста `trainingDays`. При отсутствии положительного целого норматива используется 1 день. |

Календарь сначала обрабатывает назначения с `Iкр`. Для текущего месяца поиск начинается с сегодняшнего дня, для другого выбранного месяца — с начала месяца. Суббота и воскресенье пропускаются. Лимит одновременных обучений по умолчанию равен **2**. Генератор ищет полный срок в последовательности доступных будней. Занятый день, пересечение по посту или оператору либо исчерпание дневного лимита сбрасывает набранную последовательность. Следующее обучение того же оператора начинается после завершения предыдущего.

Первое назначение, для которого не найден полный срок, останавливает автоматическое заполнение. В календаре остаются ранее размещённые назначения. Снимок сохраняет причину остановки и количества рассчитанных и размещённых назначений. Праздники отдельным календарём не учитываются.

## Ручная корректировка и сохранение

Строки календаря соответствуют постам, столбцы — дням и нормативу. Через `+` можно выбрать оператора. Меню занятой ячейки позволяет удалить обучения оператора. Редактирование столбца «Срок» сохраняет норматив поста в матрице и календаре. Допустимы целые значения от 1 до 365 рабочих дней.

Ручное добавление применяет отдельные проверки уровня и пересечений. Оно может разместить неполный срок и при расчёте будней использует текущий месяц системы. При ручных изменениях в просмотре другого месяца проверяйте фактические даты и полноту блока.

[plans-module.js](plans-module.js) формирует календарь через `generateDevelopmentPlan()`. [plans-storage.js](plans-storage.js) оборачивает генерацию и редактирование, сохраняет снимки по месяцам и восстанавливает их. При повторной генерации текущего месяца слой хранения сохраняет прошлые дни существующего снимка. Общий формат хранения описан в [README разработчика](README_DEVELOPERS.md#хранение-и-резервирование).
